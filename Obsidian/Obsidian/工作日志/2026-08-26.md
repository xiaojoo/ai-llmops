## 追加（04:32）EpisodicMemory 无数据的排查结论

**结论：不是 bug，是提取器设计使然。**

排查过程：
1. 确认 app `60198026`（小说创作助手）`long_term_memory.enable=True`，但 Weaviate `EpisodicMemory` 中该 app 零对象（4 个对象全属 记忆验证应用 e3c7a448）
2. 日志确认 `_trigger_episodic_extraction` 每轮都调用 LLM 提取器（deepseek POST 正常），但知识库类查询返回 `[]`
3. 直接调用 `extract_episodes` 双样本对照：
   - T1 知识库查询（"唐宇在其他大陆认识的女生"）→ `[]` ✅ 符合提示词设计
   - T2 用户活动对话（"我在写玄幻小说、帮我完善唐宇人设"）→ `[{'importance': 0.85, ...}]` 提取器工作正常
4. 会话 `1603a1ef-9e5a-4515-95b7-b29bff145f9b` 全部 21 条消息逐条核对：**全部是知识库检索查询**（感情线/章节/人物关系），无一例外 → 提取器按设计全部跳过

> [!info] 提取器判定依据（EPISODE_EXTRACTOR_TEMPLATE）
> 只记录"值得记住的完整体验"：长期任务、用户偏好、模式；**明确排除一次性查询/简单问答/知识库检索**。知识库查询本来就不该进记忆——信息已在知识库中，无需重复记忆。

**如何让用户验证记忆功能**：用偏好/创作类对话，例如"我喜欢唐宇和吴梦婷的感情线，以后写这类剧情前先提醒我"、"我在写玄幻小说，主角叫唐宇"——这类消息会产生 episodic 记忆。

## 追加（04:45）迭代超限丢数据的修复（用户报告"只显示重试提示"）

**现象**：小说创作助手问答"处了霓裳、青潺、烈甜、娅楠、美杜莎还有哪些其他大陆认识的女生，章节在5000章之后"（message b8163d52，20:29:31），只返回"当前Agent迭代次数已超过限制，请重试"，用户拿不到任何已检索数据。

**数据库取证**（message_agent_thought，14 条）：
- 实际执行了 **6 次 dataset_retrieval 工具调用**，Agentic 重检 trace 每轮 3→6→9→15→12→18 轮，已检索回大量知识库正文（5070章粉裙少女/炼狱大陆、10176章低等世界等）
- 第 5 轮 LLM 时 `iteration_count(6) > max_iteration_count(5)` 触发超限 → 固定文案，**全部已检索数据被丢弃**

**根因**：`FunctionCallAgent._llm_node` / `ReACTAgent._llm_node` 超限分支直接 publish 固定文案 `MAX_ITERATION_RESPONSE` 并结束，不利用 state["messages"] 里已积累的 ToolMessage。

**修复**（`internal/core/agent/agents/function_call_agent.py` + `react_agent.py`）：
- 新增 `_publish_iteration_limit_response`：超限时**不绑定工具**（用原始 `self.llm.stream`），在消息末尾追加 SystemMessage（"已达最大迭代次数，禁止再调用工具，请基于已有工具返回内容组织最终回答；信息不足时说明已获取/缺少什么"），流式生成兜底回答 + token 统计 + AGENT_END；LLM 调用异常才回退固定文案
- ReACTAgent 超限分支改为调用同一方法（移除 `_publish_end_event` 固定文案路径 + 未使用的 MAX_ITERATION_RESPONSE import）

**验证**（构造含 ToolMessage 的超限 state 直调 `_publish_iteration_limit_response`）：
- ✅ 流式输出完整回答："1. 粉裙少女（第5070章，炼狱大陆，与唐宇相识并同行）2. 灵儿（第5200章，神音大陆遇到的舞女）…目前检索到的信息仅覆盖这两处明确记载…完整名单需要更全面的章节数据才能确认"
- ✅ 不再是固定文案；语法检查通过；后端已重启加载

> [!info] 迭代上限说明
> `AgentConfig.max_iteration_count` 默认 5，app_config 未覆盖。超限判定 `iteration_count > 5` 即第 6 轮 LLM 触发。知识库多轮 Agentic 重检 + 模型反复检索容易撞上限，超限兜底回答让用户至少拿到已检索内容。

## 追加（04:52）记忆隔离性核查（用户问"账号间记忆是否互串"）

**结论：记忆按 `(app_id, user_id)` 双键隔离，账号间不会互串。** 逐路径核查 + 实证：

**存储/检索层（全部带双条件）**：
- `EpisodicMemory`（情景）：Postgres 查询（search_episodes/get_recent_text/get_episodes）均 `app_id + user_id`；Weaviate `_recall_vector`/`_recall_bm25` 均 `Filter.by_property("app_id")+Filter.by_property("user_id")`；写入 properties 带 app_id/user_id
- `UserMemoryFact`（语义）：get_current_fact/facts/at/window 全部 `app_id + user_id`
- `ProceduralMemory`（程序）：get/upsert/delete 全部 `app_id + user_id`

**读写入口**：chat_runner 召回注入（search_episodes(conversation.app_id, account.id)）、记忆工具闭包（get_tools 绑定 app_id/user_id）、写侧管道线程（user_id=account.id）、Web UI 记忆页（current_user.id）——全部按登录账号隔离。

**实证**（app 60198026，同一 query，不写库）：
| 账号 | Episodic 召回/库内 | UserFact | Procedural |
|---|---|---|---|
| 真实账号 b63ccd33 | 1 / 1 | 1 条 | 140 字符 |
| 随机 UUID | 0 / 0 | 0 条 | 0 字符 |

> [!warning] 两个边界语义（非 bug，需知晓）
> - **隔离粒度是"登录账号"，不是"浏览器访客"**：web-app/调试页 user_id = account.id（web-app 接口也 @login_required），同一账号不同终端共享记忆是预期行为
> - **开放 API 场景**：conversation 按 `end_user.id` 隔离，但 Agent 构造传 `user_id=account.id`；当前开放 API 未注入记忆工具/召回（无互串实害），若未来启用记忆需改为 end_user.id
